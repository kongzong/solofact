# solofact：记录事实，不记录判断

## 你在做什么

用户(或你自己)在一次接触、一通电话、一条承诺、一笔账、甚至一件日常之后需要留下证据：几点、跟谁、通过什么方式、说了什么、有没有数值（金额/体重/读数…）。
这些东西一旦写成散文就再也查不动——没人能从 200 条记录里算出回款总额，也看不出体重趋势。

本 skill 把每条事实变成一个 Markdown 文件，frontmatter 是结构化字段，于是 Obsidian 的 Bases 能按 who/方式分组、按 when 排序、把 howmuch 拆成正/负两本账（资金主题即进/出）。**约束的意义不是让正确的事更难做，是让错误的事失败得响亮。**

事实 = 5W2H，必填 `who` / `when` / `what`，其余（time/where/why/how/howmuch）想到了才填、不填不报错。

**主题 = 一个目录**（一堆事实的上级），不是 fact 里的字段。`--topic 潮汕6日游` 会建 `潮汕6日游/{_真源,事实,潮汕6日游.base}`，这条事实就归到那个目录。同主题内 `howmuch` 天然同一量纲（记账都是元、体重都是 kg），所以**没有 type、不校验单位**——主题从目录名推断，不写进 frontmatter。符号同理是主题级约定：资金主题 **负=出、正=进**，核心只校验"是不是数字"。

## 只有一个写入函数集

规则的实现在 `core/{fact,vault,scan,record}.js`，只有一份；壳（CLI 已可用，Obsidian 插件是已定的产品本体，
代码在 `plugin/main.ts` ＋ `core/adapters/vault.js`）不许自带第二份校验。落盘顺序（真源 → Markdown）
在 `core/record.js` 的 `openSession()` 里，两个壳共用同一个函数——它一被复制，就会出现"Markdown 有、真源没有"这种本项目要消灭的错误。
本 skill 走的是 CLI 壳：它在**本 skill 目录**的 `cli/solofact.js`，在 skill 目录根执行 `node cli/solofact.js <命令>`
（脚本按自身位置解析 `core/` 与 `contract/`，把路径写全从任何目录跑都行）。库目录用 `--vault` 或 `SOLOFACT_VAULT`。

```
init   --vault <库> [--force]     建 .obsidian、写 types.json（主题在首条记录时按需建）
记录   --vault <库> --topic 潮汕6日游 --who 我自己 --when 2026-10-12 [--time 09:30] \
       [--where 江边] [--why 记录习惯] [--how 运动] [--howmuch 5] \
       [--tags 日常] [--id …] [--recorded YYYY-MM-DD] "正文"
删除   --vault <库> --topic <主题> <id> [--yes]  唯一的破坏性写入：默认只预览，--yes 才真删
主题   --vault <库>               只读：列出现有主题和各主题事实数（录入前先对齐主题名）
体检   --vault <库>               跨所有主题汇总，写 _体检.md，有致命错误退出码 1
重建   --vault <库>               每个主题的 Markdown 从它自己的 _真源/ 重生成
导入   --vault <库> [--topic <主题>] <file.ndjson>  走同一套校验，致命的那行拒绝入库
```

- 必传：`--vault`、`--topic`、`--who`、`--when`、以及引号里的正文（`what`）。
- 一般不传、让系统生成：`--id`（自动生成，手填易撞 `E_BAD_ID`/`E_ID_DATE_MISMATCH`）、`--recorded`（默认写入当天）、`--time`（默认写入时刻或 `00:00`）。
- 退出码：成功 `0`；致命错误 `1`（stderr 含 `✗ 拒绝写入 …`）；参数/配置错 `2`。**agent 靠退出码判成败，致命时读 stderr 的 `E_ 代码 — 说明` 改字段重跑。**

写入面就这六个。**不要加写入命令，不要改脚本本体，不要"顺手修个 bug 后就接着用"。**
唯一的只读命令是 `主题`（列主题+事实数，零写入）——录入前先跑它，主题名和库里的拼写保持一致，
否则「潮汕六日游 / 潮汕6日游」这种漂移会让按主题的聚合碎成两摊。

### 删除（唯一的破坏性写入）

`删除` 默认**只预览**（打出 who/when/what，真源和 md 一个字节不动），同一命令加 `--yes` 才真删。
真删 = 真源压缩重写 + 删 `事实/*.md` + 刷时间线，**不可逆**（恢复只能靠库自己的 git）。

agent 的铁律：**用户说"删掉刚才那条"时，先跑预览、把内容念给他确认，他点头后才加 `--yes` 重跑。**
不要替用户预判"这条显然该删"——判断是他的，删除是你的手。

## 硬性规则

1. **不手改 `事实/*.md`。** 它们是读模型（在 `<主题>/事实/` 下）。字段写错了：用 `删除` 去掉那条再 `记录` 一条正确的
   （`删除` 会连真源一起清，不留复活隐患）；或者重新 `记录` 一条正确的、把错的那条留成 E_ 错误让人看见。
   手改 Markdown 的下场是下次 `重建` 时你的修改静默消失；**手删 md 更糟——真源里那行还在，重建会把它复活**，
   要删就走 `删除 --yes`（预览 → 确认 → 真删）。
2. **致命（`E_`）= 必须改数据。** CLI 在致命错误时拒绝写入并退出码 1，这是设计，不是 bug。
   被拒绝时不要绕过校验——不要为了通过而加 `--force`、改枚举、删校验行。
3. **告警（`W_`）= 需要人看一眼。** 不阻断写入，但 `体检` 会一直报到它消失或你确认它是对的。
4. **正文只写可指着说"就是这个"的东西。** 判断词（意向/大概率/风险/评分/阶段/感觉/看起来/稳了/没戏）
   会触发 W_JUDGEMENT。"客户意向很强"不是事实，"客户说下周走合同"才是。
5. **不知道时刻就写 `--time 00:00`，过去的日期用 `--when` 指定。** 不拿写入时刻冒充发生时刻，那是编数据。
6. **一条事实一个文件，id 是校验和。** `f-YYYYMMDD-HHmm-4hex` 的日期段必须等于 `when`、时间段必须等于 `time`。
   同主题内同 id 第二次写入会被拒绝——覆盖文件等于静默丢掉一条事实。（id 只需主题内唯一。）
7. **主题名 = 目录名。** 含 `/ \ : * " < > | ? [ ]` 会被拒（`E_BAD_TOPIC`），比如把主题写成 `腾讯/集采`。要区分就起两个主题，别拿斜杠。`who/where/why` 同理会因非法字符被 `E_BAD_NAME` 拒。
8. **`howmuch` 只查是不是数字（正数/零/负数都放行）。** 同主题内天然同量纲，所以没有单位/口径校验、没有 type；单位（元/kg/公里…）写进正文或 `how`。符号是主题级约定：资金主题**负=出、正=进**（记账：收款/回款记正，付款/支出记负；Sum 即净流量）——核心不判正负，它不可能知道每个主题的语义。

## 致命错误：agent 自己补字段重跑（不要抛给用户）

致命错误**几乎都是你自己填错字段**（漏必填、忘 `--topic`、主题名带 `/`、日期写错、howmuch 不是数字），不是用户的判断问题。
所以流程是：**读 stderr 里每条 `E_ 代码 — 说明` → 按下方速查表改对应字段 → 重跑 `记录` 命令**，不要停下问用户。
告警（`W_`）才念给用户、由他决定改不改。

stderr 格式是 `  <CODE> — <说明>`，说明里多半已带字段名；下表覆盖所有 `E_` 代码和"改哪个字段"。

| 代码 | 含义 | agent 改哪个字段 / 动作 |
|---|---|---|
| `E_MISSING_TOPIC` | 没给 `--topic` | 补 `--topic <主题>` 重跑 |
| `E_BAD_TOPIC` | 主题名含非法字符（`/ \ : * " < > \| ? [ ]`）或以 `.` 开头 | 换个合法主题名（用两个名字区分，别用斜杠） |
| `E_MISSING_REQUIRED` | 缺必填字段（who/when/what） | 补 message 指出的字段重跑 |
| `E_BAD_NAME` | who/where/why 含非法字符 | 改名重跑 |
| `E_AMOUNT_NAN` | `howmuch` 不是数字 | 改成数（正/零/负都行），或去掉让它是空 |
| `E_BAD_DATE` | `when`/`recorded` 不是 `YYYY-MM-DD` | 改成 `YYYY-MM-DD` |
| `E_BAD_TIME` | `time` 不是 `HH:mm` | 改成 `HH:mm`，或去掉让系统填 |
| `E_FUTURE_DATE` | `when` 在未来 | 确认日期；过去的事用 `--when` 指定 |
| `E_RECORDED_BEFORE` | `recorded` 早于 `when` | 一般不用传 `--recorded`，去掉它重跑 |
| `E_ID_DATE_MISMATCH` / `E_BAD_ID` | 手填的 `--id` 与日期/时间对不上或格式错 | 去掉 `--id` 让它自动生成 |
| `E_DUPLICATE_ID` | 该 id 已在该主题里 | 去掉 `--id` 重生成（同一条事实重记会撞 id） |
| `E_EMPTY_BODY` | 正文为空（引号里没文字） | 补正文（引号里的文本） |
| `E_BAD_JSON` | 导入时某行 JSON 坏 | 修那行 NDJSON 再导 |
| `E_NO_SUCH_FACT` | `删除` 找不到这个 id | 先跑 `主题`/`体检` 核对 id；或去掉 `--yes` 先预览 |
| `E_MISSING_ID` | `删除` 没给 id | 补上 `f-YYYYMMDD-HHmm-4hex`（预览输出里能抄到） |

告警（`W_`）速查——念给用户、不阻断：
- `W_JUDGEMENT`：正文含判断词 → 请用户改成事实描述。

## 典型流程

用户说"刚才和腾讯的张三开完会，定了预算 30 万，他说下周签"：

1. 定主题：先跑 `主题 --vault <库>` 看现有主题名，对得上就复用（拼写一致聚合才不碎）；没有就新建，比如 `--topic 一人公司CRM业务`。
2. 拆字段：who=腾讯·张三、when=今天、how=会议、howmuch=300000。
3. 正文写发生过的话，不写"他大概率会签"：`和张三过了一遍需求，确认预算 30 万，答复下周走合同。`
4. 跑 `记录`。**退出码 0** 就把 CLI 的告警（若有）原样念给用户听（"这条含判断词「意向」，要不要改成事实描述？"）；
   **退出码 1** 就按上方速查表读 `E_` 改字段自己重跑，直到退出码 0。
5. 告警让用户定夺；致命错误不要抛给用户——那是你自己的字段填错了。

一天结束时、或用户问"我这库干净吗"时，跑 `体检`，把致命错误逐条列出来，每条带文件路径。

## 边界

- 视图（表格、按谁聚合、各维度看板、时间线、正值记录/负值记录两张 howmuch 表）是 Obsidian Bases 的事，**不在 CLI 里渲染表格**。
  每个主题的 `<主题>.base` 已带多张视图，用户要改视图就在 Obsidian 里改那个文件——
  `记录`/`导入` 只在文件缺失时才写它，所以你的修改不会被"记一条"静默抹掉；会重刷它的只有 `重建`。
- 每个主题的真源 `<主题>/_真源/facts.ndjson` 是 append-only 的。它坏了从 git 恢复，改 Markdown 没用。
  唯一的例外是 `删除`（真源压缩重写）——那是显式的人决策，不是静默覆盖，且默认先预览。
- 不建数据库、不做导出 PDF、不做报表。有这些需求说明该换宿主，不是该在此加代码。
- 规则实现在 `core/{fact,vault,scan,record}.js`，只有一份——插件壳（产品本体）里也不许再写一份 validate，
  它必须复用同一套 `core/` 函数，IO 走注入的 store 适配器（`core/store.js` 的 `fsAdapter` 给 CLI，
  `core/adapters/vault.js` 的 `snapshotStore` 给插件）。这条是本项目唯一不因形态改变的护栏。
